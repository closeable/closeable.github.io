最近这一年，围绕 LLM 的工程化思路发生了一个明显的转向：从"把所有东西塞进上下文"变成"把东西组织好，按需加载"。Agent Skill（智能体技能）就是这个转向下的产物——Anthropic 在 Claude Code 里把它做成了正式机制，各类 Agent 平台也纷纷跟进。

这篇文章聊聊 Skill 到底是什么、为什么有效，以及它的边界在哪里。

## 一、问题：system prompt 的膨胀困境

写过一个复杂 Agent 的人都知道这种痛：

- 为了让模型会用某个内部工具，你得在 system prompt 里写清楚用法；
- 为了让模型遵循团队规范，你得把规范全文贴进去；
- 为了让它处理 PDF、Excel、思维导图，每种文件的处理经验都要写一段。

结果就是：system prompt 越来越长，token 消耗越来越高，而且**每一条指令都在互相稀释**——上下文里塞了 20000 字的"操作手册"，模型对每一条的关注度都会下降。更糟的是，大部分内容对当前这轮对话根本没用：用户只是想改一段代码，你却把 Excel 处理指南也带上了。

RAG 能解决一部分问题，但它的检索是**语义相似度驱动**的，"用户问简历怎么写"未必能召回"文档排版规范"这条知识，因为字面上不像。

## 二、Skill 的核心思路：目录就是上下文

Skill 的解法出人意料地朴素：**一个 Skill 就是一个文件夹**，里面放一个 `SKILL.md` 和若干辅助文件。

```
my-skill/
├── SKILL.md          # 入口：名称、描述、核心指令
├── reference.md      # 详细参考（按需加载）
├── scripts/
│   └── convert.py    # 可执行脚本（按需执行）
└── examples/         # 示例
```

`SKILL.md` 的 frontmatter 只有两个必填字段：`name` 和 `description`。

关键机制在于**渐进式披露（progressive disclosure）**，分三层：

1. **启动时**：所有 Skill 只有 name + description 进入上下文，每个可能就一两行。装 50 个 Skill，常驻开销也就百来个 token。
2. **触发时**：用户的请求与某个 Skill 的 description 匹配，Agent 才读取它的完整 `SKILL.md`。
3. **深入时**：`SKILL.md` 里可以引用其他文件，模型需要细节再去读 `reference.md`，需要精确操作再去跑 `scripts/` 里的脚本。

这其实是把软件工程里"延迟加载"的思想搬到了上下文管理上。**description 就是函数签名，SKILL.md 就是函数体，辅助文件就是它引用的库。**

## 三、为什么 Skill 比长 prompt 有效

回过头看，Skill 之所以有效，是因为它同时解决了三件事：

**1. 上下文经济性。** 知识常驻的成本从 O(全部) 降到 O(描述)，只在触发时付出完整成本。对长会话尤其明显。

**2. 关注度管理。** 上下文里永远是"与当前任务相关的那一份指令"，模型不会被无关规范稀释注意力。这和 Raft 把共识拆成三个子问题的思路异曲同工：**不要靠堆料解决复杂度，要靠组织结构**。

**3. 可组合与可共享。** Skill 是纯文件，可以进 git、走 code review、跨项目复用。团队把处理某种业务文档的最佳实践沉淀成一个 Skill，新人（以及新 Agent）直接装上就能用——这才是标题里"肌肉记忆"的意思：**把个人经验固化成可分发的资产**。

## 四、写好一个 Skill 的几条实践

写 Skill 不难，写得好有讲究：

- **description 是唯一入口**，必须从"模型视角"写：什么样的请求应该触发它？要把触发词、别名、场景都写进去。"处理表格相关的任务"不如"读取、编辑、分析 xlsx/csv 文件；用户提到表格、台账、对账时使用"。
- **SKILL.md 控制在一屏左右**，放高频指令；低频细节全部外移到引用文件。它是缓存里最热的那一层，别塞成第二篇长文。
- **能用脚本就别用文字描述**。"用如下 12 个步骤调整这个 XML 再打包"不如直接给一个 `fix.py`——模型执行脚本的可靠性远高于复述长流程。
- **一个 Skill 只做一件事**。发现你写的 Skill 里有"另外，当用户要 X 时也应该……"，那就是拆分成两个的信号。
- **避免与既有工具重叠**。如果 Agent 已有原生的文件读写工具，你的 Skill 不该重复描述怎么读文件，只该描述你的业务约定。

## 五、和 MCP、RAG 的边界

这三个东西经常被放在一起比较，其实分工很清楚：

| | 解决什么 | 类比 |
|---|---|---|
| **Tool/MCP** | 给模型**能力**（调 API、查数据库） | 函数调用 |
| **RAG** | 给模型**事实**（文档、知识库检索） | 全局搜索 |
| **Skill** | 给模型**方法论**（怎么做事的经验） | 操作手册 |

典型组合是：Skill 里描述"处理这类需求要分三步"，其中某一步调用 MCP 工具拿数据，某一步引用团队规范文档（可走 RAG 检索）。它们不是竞争关系，而是堆栈的不同层。

## 写在最后

Skill 这个概念没有引入任何新技术——就是 Markdown 文件加按需加载。它有效恰恰说明了一件事：**当前 LLM 应用的瓶颈往往不在模型能力，而在我们喂给模型上下文的方式**。

把 prompt 当代码来组织、评审、版本化，可能是这个阶段 Agent 工程最划算的投入之一。
