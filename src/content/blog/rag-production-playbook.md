RAG 的门槛低得有点误导人：一个向量库、一个 embedding 接口、一段拼 prompt 的代码，半天就能跑出"看起来能用"的效果。然后接下来三个月，你会一直在处理同一类问题——召回不全、引用错位、同一个问题昨天答对今天答错、文档更新了但答案还是旧的。

这篇不写 demo，按数据管道的顺序，把"能跑"和"可用"之间的差距拆成八件事。每一条都是可以直接落到设计里的决策。

## 一、先判断：这个场景到底该不该上 RAG

不是所有"让模型懂我的资料"都要 RAG。三个判据，命中任意一个才值得上：

| 判据 | 具体表现 | 没有它时的替代方案 |
|---|---|---|
| **规模** | 语料远超上下文窗口，全量塞不进 | 直接长上下文，省掉整条管道 |
| **新鲜度** | 文档每天在变，模型不可能重训 | 全量拼上下文，每次请求都重读一遍 |
| **隔离** | 不同用户/租户/项目看到的内容不同 | 拼上下文，但权限就得靠模型自觉 |

第三条最容易被忽略，也最致命：**只要存在权限差异，就必须在检索层做过滤**，而不是在提示词里叮嘱模型"不要泄露给没有权限的人"。模型没有可靠的"权限感"，这是工程问题，不是提示问题。

三个判据都不命中的场景，老老实实用长上下文。一套 RAG 管道带来的解析器、索引、增量更新、评测集，维护成本远高于你省下的那点 token。

## 二、解析：垃圾进，垃圾出，而且很隐蔽

大部分"RAG 效果不好"的根因在解析，但排查时总是最后才想到它。典型的坑：

- **PDF 双栏排版**：纯文本抽取会把左右两栏交错拼接，语义直接碎掉；
- **跨页表格**：表头在第一页、数据在第二页，抽出来是两段无意义文本；
- **扫描件**：没做 OCR，索引里是空的，检索永远召回不到，而你只会觉得"模型没答上来"；
- **代码块与公式**：被当成普通段落切断，模型拿到半截代码。

工程上的做法是：**解析产物要保留结构**，至少保住标题层级、表格边界、代码块边界。这些结构信息不只是为了可读，它们是后面分块和元数据的唯一来源。

顺带一件事：**元数据要在解析阶段就落库**——来源、更新时间、作者、文档类型、租户/权限标签、版本号。后期补元数据要重跑全量索引，成本高一个量级。

## 三、分块：结构感知优先，参数其次

分块参数没有普适最优值，但有可用的起点：**256–512 token、10%~15% 重叠**。真正的收益来自分块边界的选择：

- 按标题、段落、列表项切，**不要按固定字符数硬切**；
- 表格转成 Markdown 存一份，或存"表格摘要 + 原文"两份，检索用摘要、生成用原文；
- 代码块整体保留，宁可变长也不要切断。

比参数更重要的是**小-大块（父子块）** 这层设计：

子块小，向量表达的语义更聚焦，召回准；但喂给模型时上下文太碎，模型看不到前后文就会瞎猜。父子块把这个矛盾拆开：**索引用子块，命中后按 parent_id 取回父块**。代价是存储翻倍、需要维护父子映射，收益是答案完整度上肉眼可见的提升。

## 四、检索：混合检索是默认起点，不是优化项

只走向量检索的系统，通常在这三类 query 上翻车：

1. **专有名词、型号、错误码、代码标识符**——"GX-4201 报错 E1024"，向量模型会把型号当成噪声；
2. **时间性查询**——"上个月的政策"，向量相似度对时间不敏感；
3. **长尾表述**——用户用词和文档用词完全不在一个词表里，向量也会漂。

所以 BM25 和向量要**并行跑，再融合**。融合别用分数加权：两路的分数量纲完全不同（BM25 是无界正数，余弦是 -1–1），归一化之后依然不稳。用 **RRF（Reciprocal Rank Fusion）**，只看排名：

```
score(d) = Σ  1 / (k + rank_i(d))     # k 取 60 是常用默认值
```

工程上的几个细节：

- **先过滤再召回**：时间范围、租户、权限、文档类型，全部作为 metadata filter 下推到检索层。过滤放在召回之后做，会把结果裁得只剩两三条；
- **各取几百条**：BM25 top 200 + 向量 top 200，融合后再重排。召回端要宽，不然重排没有原料；
- **embedding 选型别看榜就下单**：MTEB、C-MTEB 只能筛掉明显不行的，最终要拿自己 200 条标注 query 跑 recall@10。通用榜第一的模型，在你的领域语料上不一定赢。

## 五、重排：把预算花在最后一百条上

两阶段漏斗是标配：**召回 100–200 条 → cross-encoder 重排 → 取 5–8 条进上下文**。

重排模型比 embedding 模型贵一个数量级，但只在 200 条上跑，延迟通常在 100–300ms，可以接受。反之，试图用"更大的 embedding 模型"提升召回质量，往往花了钱效果还不明显——因为向量检索的本质是双塔独立编码，query 和文档没有交互，这是结构性的上限。

几个实践点：

- 重排输入要截断（文档侧 512 token 足够），否则长文档会拖垮延迟；
- 重排分数可以做**阈值截断**：最高分低于阈值时直接走"未找到"，比硬凑 5 条更靠谱；
- 多轮对话先做**指代消解**再检索，否则"那它的价格呢"这种 query 召回的全是噪声；
- 模糊 query 生成 2–3 个变体并行检索，收益明显，但要控制并发和缓存。

## 六、生成：引用是纪律，不是装饰

RAG 的产出物不只是答案，还有**可核验的出处**。强制引用格式（`[1] [2]`），并给上下文里每条内容分配稳定 id，然后守住两条规则：

- **引用不存在的编号 = 幻觉**，直接计入负例，不要人工放过；
- **空召回要显式降级**：明确说"资料里没有"，比让模型基于常识硬编安全得多。空结果还要分两类打点——"真没有"和"过滤条件写错了"，后者是工程 bug。

还有一个容易忽略的细节：**上下文顺序影响答案质量**。把最相关的放在开头和结尾，中间放次要材料（lost in the middle 现象），同样的材料，答案完整度会不一样。

## 七、评测：没有评测集，所有优化都是玄学

这是最容易被跳过、也最该先做的一步。不要等系统上线再做评测，**在第一次调参之前就要有评测集**：

- 从真实用户 query 里抽样，不要自己编——自己编的 query 会不自觉地贴合系统的能力边界；
- 规模 100–300 条起步，每条标注"期望引用的文档 / 答案要点"；
- 分层看指标：检索层看 recall@k、MRR，生成层看忠实度（答案能否被引用内容支撑）和引用准确率。**检索不过关时，改 prompt 是浪费时间**。

每次变更——换 embedding、调分块大小、改重排模型、动 prompt——都跑同一套评测集，把它当回归测试用。这一步做到了，很多"感觉变好了"的改动会被数据直接否掉。

## 八、运维：RAG 是一个有状态的系统

搜索引擎的运维经验在这里基本都适用，因为 RAG 本质上就是一个带状态的数据管道：

- **增量更新**：按文档内容 hash 判断变更，只重嵌入变化的块，别全量重建；
- **删除要同步**：文档下线了，向量和倒排都要删。这是最常漏的一条，漏了就会答出"已删除的旧制度"；
- **权限变更 = 整篇重索引**：metadata 变了，索引里的过滤标签也得跟着变，否则就是越权召回；
- **缓存**：query 级结果缓存 + embedding 缓存。重复问题占比通常远高于预期，这一层几乎白赚；
- **监控四个数**：检索延迟、空结果率、引用率、点踩率。空结果率突然上涨，八成是索引或解析挂了，而不是"模型变笨了"。

最后一句话总结这八件事的关系：

**RAG 的复杂度不在模型，在数据管道。** 解析、分块、过滤、评测这些"无聊"的环节做扎实，收益远大于换一个更强的生成模型；反过来，管道上的窟窿，靠模型是补不上的。
