半年下来，多数团队用 AI 编码助手的方式还是"散装"的：每个人在自己终端里开着 Claude Code 或 Codex，各自对着一个对话框说话。产物散在本地目录里，过程没人看得见，换个人接手就断了上下文。

Multica 想解决的就是这一层：**agent 不是对话框，是团队成员**。它把"派活—执行—汇报—复盘"这套原本用在人身上的协作流程，套到 agent 头上。

GitHub 上 57.3k star（2026 年 11 月）、背后是做 devv.ai 的那支团队。这篇文章拆开看它到底怎么实现的，以及哪些地方值得抄、哪些地方要小心。

## 一、它到底是什么：不是 workflow 编排，是项目管理系统

很容易把它和 n8n、Dify 那类东西混在一起，但定位完全不同：

- **workflow 编排**（n8n / Dify）：用画布把 LLM 调用串成流程，节点是确定的，适合"固定的业务流程自动化"。
- **Multica**：节点是"人和 agent"，核心是**任务**。任务有负责人、有讨论、有状态、有执行记录，跟 Jira/Linear 里的一条 issue 长得很像——只是负责人可以是 agent。

它也不提高单个 agent 的能力上限。你机器上装的还是那个 Claude Code，Multica 管的是：谁在什么时候、用哪套配置、在哪台机器上干活，以及干完之后结果落在哪里。

名字来自 **M**ultiplexed **I**nformation and **C**omputing **A**gent，致敬 60 年代的 Multics——分时系统让多个用户共享一台机器。他们的说法是：今天被"分时"的，除了人还有 agent。

## 二、架构：云端管协调，本地管执行

这是整个设计里最值得看的一点——**它不替你跑模型，也不碰你的代码**。

  <figcaption>图 1：上云的是任务和状态，不上云的是代码、凭据和真正的执行。</figcaption>
</figure>

**云端（协调层）**，从仓库结构看得很清楚：

| 组件 | 技术选型 | 职责 |
|---|---|---|
| `server/` | Go（pgx + PostgreSQL） | REST API、任务、队列 |
| `apps/web` | Next.js | Web 界面 |
| `apps/gateway` | NestJS | WebSocket 长连接网关 |
| 桌面端 | Electron | 本地客户端 |
| collab 服务 | Yjs + Tiptap | 多人实时编辑 |

**本地（执行层）**：一个常驻的 `daemon` 进程 + 若干"运行时"。`multica setup` 会扫描机器上已装的编码 CLI——Claude Code、Codex、Cursor、Copilot、Gemini、Kimi、OpenCode、OpenClaw 等等，每个注册成一个 runtime。

官方口径在不同页面不太一致：官网 FAQ 说"开箱支持 12 种"，仓库 README 现在写的是 **31 种**。以仓库为准，但这也侧面说明这东西迭代很快。

**数据边界值得单独说**：工作区、任务、评论、状态在云上；AI 编程工具的凭据、代码目录、实际的文件修改和命令执行，全都在你自己的机器里。文档里明说了唯一的例外——智能体 `custom_env` 里的内容会存到服务端，所以"不希望离开你电脑的 secret 不要写进 custom_env"。

这条边界决定了它的适用场景：客户代码、内部系统、有合规要求的仓库，都能用，因为代码根本没上传。

## 三、一次运行是怎么走完的

理解了"运行时"这个概念，剩下的就顺了。**智能体是身份，运行时是执行它的那台电脑**——智能体本身不是常驻进程，只在被触发时跑一次。

<figure>
  <img src="/images/multica-run.svg" data-src-light="/images/multica-run.svg" data-src-dark="/images/multica-run-dark.svg" alt="一次运行的链路：触发创建运行入队，daemon 领取后在本地调用 AI 编程工具执行，结果写回任务时间线；无在线运行时则排队等待，失败可重试" loading="lazy" />
  <figcaption>图 2：五步链路。注意两个虚线：没有在线运行时就在队列里等，运行失败可以重试。</figcaption>
</figure>

1. **任务提供上下文**：任务里存着工作说明、讨论和负责人。分配给 agent 后，系统取用这个 agent 的指令、模型、skill 和运行时配置。
2. **创建运行并入队**：一次触发 = 一条 run 记录，带着完整配置进队列。
3. **运行时领取**：某台在线机器上的 daemon 心跳正常，就从队列里领走这条 run。
4. **本地执行**：调用配置里指定的 AI 编程工具，工具读工作目录、跑命令、生成结果。
5. **结果写回**：进度、评论、执行日志全部回到任务时间线，团队成员都能看到。

触发方式有四种：**分配任务、评论里 @ 智能体、直接对话、自动化**（定时或外部事件）。四种方式殊途同归——都产生一条运行。

这里有个容易被误读的设计，文档专门强调过：**运行结束 ≠ 任务完成**。执行日志显示"已完成"，只代表这一次运行跑完了；任务还能继续讨论、补充要求、再次触发。这个区分很重要，否则很容易把"agent 说它做完了"当成"事情做完了"。

## 四、核心抽象：智能体是一份配置，skill 是可复用资产

<figure>
  <img src="/images/multica-agent.svg" data-src-light="/images/multica-agent.svg" data-src-dark="/images/multica-agent-dark.svg" alt="智能体组装模型：Skill 库可挂载给多个智能体，智能体由指令、模型、skill 和运行时组成；小队由 leader 智能体协调成员 agent 与人类成员" loading="lazy" />
  <figcaption>图 3：指令定义"这个人是谁"，skill 说明"这类活怎么做"——后者可以跨智能体复用。</figcaption>
</figure>

这套抽象里，我认为最有价值的是 **skill 的复用边界**：

- **指令（instructions）**：定义这个 agent 是谁——角色、语气、边界。
- **skill**：定义"这类工作怎么做"——一套流程、一份检查清单、一个脚本。可以挂给多个 agent 共用。
- **运行时**：在哪儿执行。
- **小队（squad）**：一个 leader agent 带若干 agent 和人类成员，任务派给小队，由 leader 拆解协调。

区别在于：**指令是私有的（身份），skill 是共享的（方法论）**。写周报的运营助手和盯 PR 的代码助手，可以用同一个"输出规范"skill。团队里某个人摸索出一套好用的做法，沉淀成 skill 之后，所有人都能挂载——这是它相对于"每人各开一个对话框"最大的结构性优势。

## 五、优势：四个真站得住的点

**1. 代码不出域，这是硬优势**

执行在本机，代码和凭据不上云。对有客户代码、有合规要求、甚至只是"不想把公司仓库传给第三方 SaaS"的团队，这一条基本决定了选不选它。而且自托管之后，连任务数据都在自己网络里。

**2. 把散装 agent 收编成可管理的资产**

以前的状态是：谁本机装了什么 agent、什么版本、跑过什么，没人知道。现在是：统一的 agent 列表、统一的运行记录、统一的日志。谁在什么时候让哪个 agent 干了什么，时间线上有痕迹。这对"agent 干了坏事要回溯"这种场景是刚需。

**3. skill 复用 + 小队，把个人经验变成团队能力**

前面说过，这是它最有想象力的一块。agent 多了之后，最大的浪费不是 token，而是每个人都在重复教 agent 同样的事。skill 让这件事只教一次。

**4. 开源可审计，可自托管，可自带模型**

Go + Next.js，Docker Compose / 单二进制 / Helm 三种部署方式，自带 LLM provider，API 可扩展。不需要把整个协作流程押在一个黑盒 SaaS 上。

顺带一个细节挺有意思：仓库里大量提交是 AI agent co-author 的（Cursor、Claude 等），他们自己就在用自己这套东西开发。

## 六、劣势：五个必须知道的前提

**1. 不是 OSI 意义上的"开源"**

许可证是 Multica License（持有方是 Index Labs (Hong Kong) Limited），属于 **source-available**：代码可读、可自托管、可改，但**限制托管使用和嵌入销售**——如果你想拿它对外提供服务，或者打包进你卖的产品，得去谈商业许可。官方文案也从"open source"改成了"source-available"。企业选型时这条要过法务。

**2. 成熟度：跑得很快，也意味着会晃**

941 个开放 PR、6,700+ commits、一个月内文档口径就能对不上（12 种 runtime vs 31 种）。数据结构、API、概念都可能变。想深度定制的团队要有跟着改的预算。

**3. daemon 必须在线，本质不是弹性云**

运行得靠某台在线的机器领走。笔记本合盖、机器休眠、公司网络断了，任务就在队列里等着。它不是"提交上去云端无限并发"的那种服务——**并发上限就是你的硬件上限**（官方明说"无人工限制，取决于你的机器")。云 runtime 还在 waitlist 阶段。

**4. 抽象成本不低**

工作区、项目、任务、对话、自动化、收件箱、小队、skill、智能体、运行、运行时——11 个概念。对两三个人的小组，前期理解成本可能大于收益；它更适合"agent 数量已经超过 3 个、开始管不过来"的团队。

**5. 费用和风险都归你**

模型 token 自己买单，没有内置的成本闸门；执行在本地，也就没有强沙箱——agent 跑错命令、删错目录，后果是真实的。任务边界靠人写清楚，写不清楚，agent 就真的会去猜。

## 七、谁适合用

**适合**：3 人以上、已经有多台机器多个 agent、开始出现"谁在跑什么说不清"的团队；有代码不能出域要求的；愿意自己维护一套服务的。

**不适合**：只想让 agent 帮自己写点代码的个人（直接用 Claude Code 更省事）；需要云端弹性并发跑几十个任务的；法务对许可证敏感的（先谈许可）。

## 写在最后

Multica 押的判断是：**瓶颈已经从"agent 会不会干活"转移到了"怎么管一群会干活的 agent"**。这个判断我认同——真按小时算，团队里浪费在"重新解释一遍上下文"上的时间，已经超过 agent 本身跑得不够快带来的损失。

但它也带来一个新问题：任务被切得越来越细、执行越来越快之后，**人反而成了流水线上最慢的那一环**。工具解决的是排班，没解决判断力。这一点，Multica 帮不上忙。
