这篇文章是我做第一个微信小程序的完整记录。题目是「养老金测算器」——一个很窄、很土、但需求真实的工具。全程没有手写一行代码，核心开发一个下午，打磨两天，我的角色从"开发者"变成了"产品经理 + 验收人"。

踩过的坑都在下面，包括一次被微信直接拦下的提审失败。

## 一、先想清楚做什么

动手前只做了一件事：定方向。选养老金测算器，三个理由：

- **需求真实**。几乎人人都关心"退休后每月能领多少"，但官方计算器入口深、参数看不懂、术语一堆。
- **逻辑清晰**。核心就是一套公开的官方公式，AI 算得比人准。
- **不碰红线**。纯工具类，不涉及交易、支付、社交，个人主体就能做。

第一版的功能清单只有四条：

1. 选城市，自动带出当地养老金计发基数
2. 填年龄、缴费年限、缴费指数，一键测算
3. 保存方案，随时回来对比
4. 结果一键分享，好友点开能直接算自己的

原则只有一条：**第一版只做核心功能**。分享卡片、图片识别这些，都是核心跑通之后一句一句加出来的。

## 二、准备工作：比想象中短

### 1. 注册账号

打开 `mp.weixin.qq.com` → 立即注册 → 选「小程序」。个人主体用身份证 + 邮箱即可，**不需要营业执照**。注册完记下 AppID，后面全程要用。

这一点值得强调：很多人卡在"我没有公司"上，其实个人主体能做的东西比想象中多，只是不能涉及经营性服务和支付。

### 2. 开发环境

没有装开发者工具写代码。直接在 WorkBuddy 里说需求："帮我做一款微信小程序，计算养老金"，它会生成完整项目结构——页面、样式、逻辑、配置一次到位。

工具类小程序的标准结构是四层，知道每层管什么就够了：

| 层 | 文件 | 干什么 |
|---|---|---|
| 页面结构 | WXML | 界面骨架 |
| 页面样式 | WXSS | 外观皮肤 |
| 页面逻辑 | JS | 处理输入、调用计算 |
| 全局配置 | JSON | 注册页面、声明权限 |

这几层你不需要自己维护，但需要知道出了问题该看哪一层。你的真正工作是**验收**：每次改动后看预览、提意见、让它改。

### 3. 把公式交给 AI

养老金的官方公式：

```
月基本养老金 = 基础养老金 + 个人账户养老金

基础养老金 = (当地社平月工资 × (1 + 平均缴费指数) / 2) × 缴费年限 × 1%
个人账户养老金 = 个人账户累计储存额 ÷ 计发月数
```

计发月数是官方固定表：60 岁退休对应 139，55 岁对应 170，50 岁对应 195。

把公式原样贴给 AI，它会封装成独立的计算模块。这里有个关键要求：**计算和界面分开**。后面加分享预览、多方案对比时，计算模块零成本复用。

另外有两个验收点必须一开始就提：

- **输入校验单独做**。年龄范围、指数上限、年限上限都要拦，报错得说人话（"退休年龄需大于当前年龄"），不能让页面崩掉。
- **少缴 15 年出警示**。这是用户最容易忽略、也最容易误解自己养老金的地方。

## 三、城市数据：别让用户手填社平工资

"退休时当地计发基数"是公式里最难填的参数——用户根本不知道自己城市是多少，也不知道该查哪个文件。

我的需求只有一句："**当地社平工资不要让用户填，可以选城市，内置最新数据**"。AI 内置了 33 个主要城市的计发基数表，点选城市自动填入，并记住上次选择。

> ⚠️ **血泪教训**：最初想做得更聪明，用定位自动匹配城市。结果发布时被微信直接拦下——"使用了未申请权限的隐私接口"。定位属于需要单独申请资质的敏感接口，工具类小程序大概率驳回。最后把定位整个删掉，改成"手动选城市 + 记住上次选择"，一次审核问题都没有。
>
> 结论：**在微信小程序里，能手动操作的就不要碰敏感权限。**

## 四、表单重构：把复杂留给自己

AI 的第一版把六个输入框全怼在用户脸上：当前年龄、退休年龄、缴费年限、缴费指数、社平工资、个人账户余额。能用，但体验很差——用户打开就不知道该从哪填。

重构需求是这么说的："**分成两块——已缴费的通过图片读取，未来缴费的填年限和档次，其他数据都自动算好**"。改完是三层：

1. **已缴费情况**：上传社保权益单自动识别，不想上传也能手填
2. **未来缴费计划**：只选未来打算缴的年限和档次（0.6 / 0.8 / 1.0 / 1.5 / 2.0 / 3.0 六档，配通俗标注如"足额缴""顶格缴"）
3. **自动汇总**：已缴 + 未来合并，算出退休时的缴费年限、平均缴费指数、个人账户总额

这次改动给我留下的方法论是：

> **用户不会算的，替他算；用户说不清的，给选项而不是给输入框。**

而且这句话是可以直接说给 AI 听的。它不需要你讲"重构表单组件"，它需要你讲产品意图。

## 五、加分项：拍一张社保权益单，自动填表

社保权益单（电子社保卡 App、12333 小程序里都能查到）里包含累计缴费月数、个人账户储存额等关键字段。于是我提了个需求："用户上传社保缴费单，能提取到哪些信息？识别后直接填进去。"

AI 实现的链路是四步：

1. 用户拍照或从相册选图
2. 图片发给视觉模型，要求只输出结构化结果
3. 识别出的缴费年限、账户余额自动回填，平均缴费指数同步推算
4. 识别失败保留手动填写入口

三条经验：

- **识别要求要写得具体**。只说"提取缴费信息"识别率很低，说清"只提取测算需要的字段，平均缴费指数尽力推算"，准确率明显不同。
- **隐私要如实声明**。图片只用于实时识别、不落库、不留存——这句话写进隐私指引，审核时才能对上。
- **入口要简单**。最初给了三种找单方式，用户反馈"步骤太复杂、没耐心"，最后精简成两种，并直接说明在哪看、找到哪一页。

## 六、保存方案：一个功能的三轮打磨

用户常想"多算几种情况对比"。需求是"测算完能保存方案"，AI 用本地存储实现了保存、载入、删除。

**个人工具类需求，本地存储就够了，不需要搭服务器。** 这一条能省掉后端、账号体系和一整套审核材料。

但功能做完不等于好用，这个功能磨了三轮：

| 轮次 | 问题 | 改法 |
|---|---|---|
| 一 | 保存后没有任何反馈，不知道存没存上 | 保存后立即在页面显示刚存的方案 |
| 二 | 每次都要给方案起名，太麻烦 | 默认自动命名，允许手动改 |
| 三 | 重算或重置时旧结果还在，容易误导 | 重算即清掉展示 |

**AI 的第一版往往是"能用"，好不好用要靠你盯着细节提需求。**

## 七、最难啃的部分：分享

分享是小程序的获客命脉，也是踩坑最多的地方。整个过程四个回合。

### 回合 1：分享出去没图

第一版分享只有标题没有缩略图——因为不设缩略图时微信会随机截屏，截到什么算什么。

解法：测算完成后用画布预先生成一张 5:4 的结果卡片（带金额、构成明细），分享时直接用；同时内置一张静态兜底图，保证任何情况下转发都有图。

这一步踩了三个技术坑：

- 隐藏画布的方式不对，导出是空白图
- 旧版画布组件在真机上导图失败，还会突然盖在页面上
- 分享是同步动作，等不了异步画图，必须**提前**画好

### 回合 2：按钮兼容性

两个按钮放一起，出现离得太近、一大一小、文字折行。微信的按钮组件自带历史包袱：默认边框、默认间距、flex 挤压。

这类问题肉眼很难一次说清。我的做法是拉测试、开发、产品三个角色对一遍，把"布局挤压、样式覆盖不生效、文字折行"逐个定位。用 WorkBuddy 开团队，一句"看一下兼容性"就能让多个 AI 角色交叉检查——比一个人盯着找快。

### 回合 3：分享图该放什么信息

用户的要求是"可以展示最后计算的部分，具体你优化"。最终版本：大字号金额 + 基础养老金/个人账户构成 + 城市与退休年龄。目标是扫一眼就知道"这是算出来的什么数"。

### 回合 4：好友点开之后

这是产品决策上最关键的一处。最初好友点开分享，看到的是分享者的参数和结果，很容易误以为是自己的数据。

用户反馈很直接："打开后自己填参数就行"。最终交互：

- 好友的参数只用于展示一条轻量的"好友测算结果 · 仅供参考"预览
- 表单恢复默认值，让好友直接填自己的
- 一个醒目按钮「填我的参数，重新测算」，点击后重载干净首页，有明确的"跳转"感

> **分享的终点不是"能分享出去"，而是"对方愿意接着用"。**

## 八、UI 打磨：几个必踩的坑

即使全程用 AI 开发，这些坑照样会出现。知道它们存在，能让你更快定位问题：

| 现象 | 原因 | 处理 |
|---|---|---|
| 按钮离得近、带框、大小不一 | 微信按钮组件自带默认边框与间距 | 清默认样式，统一高度和间距 |
| 并排按钮文字折行 | flex 挤压长文字 | 固定宽度 + 禁止折行 |
| 自定义样式不生效 | 组件默认样式优先级更高 | 选择器写得更具体 |
| 画布突然盖住页面内容 | 旧版画布是原生组件，层级高于页面 | 换新版画布组件 |

这些问题的共同解法是：**截图 + 描述现象发给 AI，让它自己排查**。AI 做静态检查（结构配平、语法校验）比人眼快得多。

## 九、发布提审：最后一公里

代码写完只是 80%。发布环节有自己的规则，每一条都是真实撞上的。

### 1. 代码包体积 ≤ 2MB

第一次提审直接失败——开发过程中生成的图片素材把包体撑爆了。解法：让 AI 把非代码资源从打包配置里排除，包体降到 1MB 以内。

### 2. AppID 必须是正式的

用测试号（游客模式）永远无法发布。上传体验版前，确认开发者工具里填的是正式 AppID。

### 3. 隐私保护指引要一一对应

用了相册、相机等能力，必须在公众平台的隐私保护指引里逐项声明用途，文案要如实（"图片仅用于实时识别，不保存、不留存个人信息"）。

**代码里调了但指引里没声明，提审必拒；代码里没用却声明了，会被要求提供资质。** 两边必须对齐。

### 4. 敏感权限能不用就不用

定位那条教训再强调一次：这类接口需要单独申请，工具类小程序很难通过。**设计阶段就避开敏感权限，是效率最高的合规策略。**

### 5. 发布流程

```
开发者工具上传 → 公众平台设为体验版（拉体验成员）
→ 提交审核 → 通过 → 发布线上版
```

体验版只有体验成员能打开；要让所有好友可用，必须走审核发布。个人主体、非经营性工具类，审核通常 1~3 天。

顺带回答两个高频疑问：**个人主体可以备案**（不需要营业执照，仅限非经营性服务）；**备案不影响失业金领取**。

### 6. 真机验证别跳过

模拟器和真机是两个世界。真机上遇到过"运行环境加载失败"、画布导图失败——模拟器里完全看不出来。发布前至少 iOS 和 Android 各找一台真机走一遍主流程。

## 十、回看：我的角色变了

从第一句"帮我做一款小程序"到可提审的完整产品，核心开发一个下午，打磨两天。全程没有手写代码，真正花时间的是四件事：

1. **把需求说成人话**。不说"重构表单组件"，而是"已缴费的用图片读，未来的填年限和档次，其他自动算好"。AI 听得懂产品语言。
2. **盯着细节验收**。AI 的第一版永远"能用"——保存没反馈、分享没图、按钮一大一小，这些都要你像用户一样用一遍、截图反馈。
3. **合规前置**。敏感权限、隐私指引、包体积，在设计阶段就想清楚，比提审被拒再返工快得多。
4. **每个功能都要有兜底**。识别失败能手填、画图失败用静态图、链接失效有提示——工具类产品的口碑就藏在这些"失败了也没关系"里。

小程序的技术门槛比想象中低得多。最难的不是代码——代码可以交给 AI——是想清楚"用户到底为什么要用你的东西"。

这条判断值得多说一句：当一个工具里最贵的部分从"实现"变成"想清楚"，能做的事情的量级就变了。以前一个想法要先问"我做得出来吗"，现在要问"这个想法值得做吗"。

祝你的第一个小程序早日上线。
