可观测性不是“多打日志”

2026 年 10 月 5 日 约 2 分钟阅读

指标、日志和链路追踪解决的是不同问题。分清它们的分工，才能在排障时少走弯路。

系统出问题时，我们最常做的第一件事是翻日志。但日志只能告诉你“某一刻发生了什么”，很难回答“这个问题从什么时候开始”“影响范围有多大”。

三类信号，三个问题

  • 指标（Metrics）：可聚合的数字。回答“有多少”“多快”“错误率多少”。
  • 日志（Logs）：离散的事件记录。回答“具体发生了什么”。
  • 追踪（Traces）：一次请求跨越服务的完整路径。回答“时间花在了哪一跳”。

它们不是互相替代的关系，而是从三个角度描述同一个系统。

指标：先定义 SLI，再决定采集什么

很多团队采集了几百个指标，真正排障时却找不到关键数据。原因通常是采集在前、问题在后。

更靠谱的顺序是：

  1. 先定义用户可感知的服务指标，例如请求成功率、P99 延迟。
  2. 再确定哪些内部指标能解释这些 SLI 的变化。
  3. 最后才决定用什么工具采集。

对 HTTP 服务来说，RED 方法是一个不错的起点：Rate（请求速率）、Errors（错误数）、Duration（耗时分布）。

日志：结构化、带上下文

排障时最怕的是日志里只有一句 something went wrong。建议：

  • 使用结构化日志（JSON），而不是拼接字符串。
  • 每条日志带上 request id、trace id 和用户标识（脱敏后）。
  • 区分错误级别：预期内的业务失败不该记作 error。
{
  "level": "warn",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "event": "downstream_timeout",
  "service": "order-api",
  "upstream": "inventory-svc",
  "duration_ms": 812
}

追踪：解决跨服务归因

当一次请求穿过五六个服务，日志里的告警只能告诉你“某个环节慢了”，追踪能直接告诉你“是 inventory 服务的第三次数据库查询慢了”。

接入链路追踪的成本主要在传播上下文：HTTP header、消息队列的 message header 都要带上 trace 信息。一旦打通，排障效率会明显提升。

小结

不要试图用一种信号解决所有问题。指标用于发现，追踪用于定位，日志用于确认细节。 三者配合，才构成完整的可观测性。
